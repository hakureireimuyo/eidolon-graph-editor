# 节点视觉渲染方案 v2 —— 从内核语义推导的全新布局

> 替代现状(v1 矩阵方案)。核心立场:**节点长什么样,应该由内核声明推导,而不是由编辑器自创一套与语义无关的排布规则。**
> 相关:内核 `model/node.py`(NodeType)、`model/types.py`(端口/组)、`engine/snapshot.py`(运行快照)。

---

## 0. 为什么废弃 v1(矩阵方案)

v1 的核心视觉单元是"端口行":40px 一行、每行一个输入或输出端口、信号/数据双句柄 ±6px 上下配对、左右两列对齐成矩阵。批判:

| v1 问题 | 语义根源 |
|---|---|
| **行对齐是虚构的**。输出 j 排在"组内末输入行 + j",这个偏移量是编辑器发明的,内核没有"输入和输出同一行"的语义——真实对应关系是**组(方法)**:输入→输出经由方法,不是经由行号 | 内核:`输入组 = 方法,输出组 = 返回值`;组间参数不互传 |
| **节点形态被抹平**。AND/NOT/Latch(纯信号元件)与 LlmCall(异步数据节点)渲染成同一个矩形+行列表;内核却明确提供了形态派生(`is_signal_node()`、`is_source()`) | 内核:`control_out` 声明 = 信号节点;`auto`/无组 = 源 |
| **方法身份很弱**。组 = 方法是内核第一结构概念,单组节点完全不显示;多组才有一个细边框小标题;触发策略(⚡ vs 齐到 vs 任一)完全不可见 | 内核:`InputGroup.policy` 四种策略 |
| **触发入口是孤儿**。黄色句柄浮在组框左缘垂直中间,与任何文字无关 | 内核:`TriggerIn` = 函数调用级激活入口 |
| **控制端口混进方法矩阵**。enable/level 输入是**节点级**门控/组合线,不是方法参数,却和参数并排一行 | 内核:`ControlIn.semantic`(enable=门控整节点,level=纯电平组合线) |
| **stray 虚线框**。多组节点的控制端口落进一个无名虚线框,读起来像"剩料回收站" | 编辑器自创,内核无此概念 |
| **运行状态不上脸**。count、remaining、lines 这些最"活"的字段只在侧栏;熔断、pending 完全不可见 | 内核:`NodeSnapshot`(state/fresh/熔断) |
| **固定 40px 行高撑高节点**。Counter 三行就 120px+,画布密度低,图一大就难扫 | — |

**结论**:v1 的形态是从"怎么画一行端口"出发自下而上堆出来的;v2 从"内核声明了什么语义"自上而下推导布局。两者几乎处处相撞,故整体重写,不修补。

## 1. 设计推导:语义 → 视觉隐喻

```
内核语义                            视觉隐喻
──────────────────────────────────────────────────────────
节点类型 = 类                        节点 = 一个小型"器件卡片",头部 = 类名
输入组  = 方法(参数)                每个组 = 一条水平"方法带":
                                      [参数] 方法名 → [返回值]
输出组  = 方法的返回值                ← 方法带是节点布局的核心单元
组间参数不互传                        ← 方法带彼此独立,互不对齐(布局即语义)
TriggerIn = 函数调用级激活入口        ⚡ 闪电符号挂方法名旁(黄色 = 调用入口)
触发策略 = 怎么产生 activation        → 方法名与输出之间的连词符形态
ControlIn = 节点级门控/组合线        单独一条"信号栏",不混进方法带
ControlOut = 信号输出(信号节点身份)   信号栏本身 = 信号节点的身份标记
数据端口自带信号电平                  数据点 ● 上方伴一个迷你信号环 ◯
StateField = 实例字段(世界事实)      运行读值带:name=value 实时上脸
ConfigField = 只读旋钮                配置带:只显示被实例覆盖的值
auto / 无组 = 源                     头部 ▶ 徽标 + 自产输出带
impl 子图/脚本                       ⊞ / ⌘ 徽标
```

两条硬规则:

1. **布局由声明派生,零硬编码**:任何新节点类型(包括未来的子图/脚本节点)按同一套规则自动获得正确形态。编辑器不维护节点清单,与后端 `node_types_payload` 同源。
2. **布局即语义**:方法带独立 ⇔ 组间不互传;信号栏独立 ⇔ 数据/信号不互通(只在 Trigger 层汇合)。视觉上不该出现语义上不存在的结构(如 v1 的行对齐)。

## 2. 节点解剖学:四条带

```
┌──────────────────────────────────────────────┐
│  ▤ Join        [形态徽标]              n3ab   │ ← 头部带 identity
├──────────────────────────────────────────────┤
│  (a) (b)  join → (out)                       │ ← 方法带 每组一条
│                                              │   (核心单元,见 §3)
├──────────────────────────────────────────────┤
│  ◯enable           ◯out  ◯failed             │ ← 信号栏 节点级控制端口
│                                              │   (信号节点的身份,见 §4)
├──────────────────────────────────────────────┤
│  ●count ◯sig  ·自产                          │ ← 源产出带 auto 节点的
│                                              │   未入组数据输出(见 §5)
├──────────────────────────────────────────────┤
│  count=12 · lines=5                          │ ← 运行读值带 运行时
│                                              │   state 上脸(见 §6)

不是所有带都存在:带是否出现完全由声明决定(见 §7 决策表)。
行高 26px、头部 26px——节点面比 v1 紧凑约一倍。
```

## 3. 方法带(核心单元)

```
  [参数端口…]   ⚡方法名 连词符 [返回值端口…]
  ──────────────────────────────────────
  (int_a) (int_b)  g1 → (out_p)         多输入齐到(默认 on_all_data_ready)
  (int_c)        g2 → (out_q)           单输入
  (put)  put                            空方法(无返回值,右侧空白)
  (delay)  ⚡arm → (remaining) (out)    带触发入口 + 齐到策略
               ⚡flush → (items)        on_trigger:闪电就是连词符
```

规则:

- **每输入组一条方法带**,顺序 = 组声明序;组内 `inputs` 数据端口按声明序横排,输出端口同右。
- **方法名 = 组名**,是带上的文字锚点。多组节点靠名字区分(替代 v1 的框标题)。
- **触发入口 ⚡** 挂在方法名**左侧**(参数与名字之间):语义 = "调用这个函数的入口",靠近名字。句柄 `in:trigger:{名}` 画在 ⚡ 上。
- **连词符 = 触发策略**(组 `policy`,四种):
  - `on_all_data_ready` → `→` 实线箭头
  - `on_any_data` → `↝` 散开箭头
  - `on_trigger` → `⚡` 闪电即连词符(方法名右侧直接输出端口)
  - `on_data_and_trigger` → `⚡→` 闪电 + 箭头
- **optional 参数**标签后加 `?`(灰):`(in?)`。
- **绑定端口**:`const` 默认 → 标签前缀 `=`,如 `(rate=1)`;全局读取 → 前缀 `@`。绑定端口不参与触发,点旁以不同深浅表达(绑定输入稍暗,提示"不依赖连线")。

### 端口字形

| 字形 | 含义 | 颜色 | 连接句柄 |
|---|---|---|---|
| `●` 实心点 | 数据端口(值载体) | 蓝 | `in:data:{名}` / `out:data:{名}` |
| `◯` 空心环 | 信号端口(电平载体) | 橙 | `in:signal:{名}` / `out:signal:{名}` |
| `⚡` 闪电 | 触发入口(调用级激活) | 黄 | `in:trigger:{名}` |
| 迷你 `◯`(数据点上方 4px) | 该数据端口自带的信号槽/信号口 | 橙 | `in:signal:{名}`(与数据槽同端口名) |

- **环 vs 点**是信号/数据的首要区分(形状差,不依赖颜色;色弱友好)。
- 数据端口自带信号面:`●` 上方 4px 一个迷你 `◯`,与 v1 同理(信号上、数据下)但间隙减到 4px、行高 26px。输出侧同理(数据点 + 上方信号口)。
- 门控语义区分:enable(门控)输入画成 `▢` 小方块(闸门感),level 输入画 `◯` 环——两种 `ControlIn.semantic` 不靠文字也能区分。
- 运行中电平:环内填色(绿=高 / 红=低),与 v1 一致。

## 4. 信号栏(节点级控制端口带)

```
  [◯/▢ 控制输入…]        [◯ 控制输出…]
  ────────────────────────────────────
  ▢enable                 ◯out        Counter(只有输入)
  ◯start ◯stop            ◯running    Timer(电平输入 + 输出)
  ◯a ◯b                   ◯out        AND(纯信号元件,无方法带)
  ◯set ◯reset             ◯q          Latch
```

规则:

- **所有 control_in / control_out 唯一归宿 = 信号栏**,永不混进方法带(它们是节点级端口,不是方法参数)。
- 输入环左、输出环右,单行排布(控制端口数量天然少,≤3 常见)。
- 信号栏背景带微弱橙色底纹(level 域的身份色),与数据方法带区分。
- **纯信号节点(无任何组,如 AND/OR/NOT/Latch)= 头部 + 信号栏**,只有 26px 高——"电平函数"的形态一眼可辨。

## 5. 源产出带(auto 节点的未入组数据输出)

auto 节点的自走 step 直接产出数据(Clock 的 `count`、Simulate 的 `result`),不属于任何组的 `outputs`。这些端口排成独立带,左端标注「自产」:

```
  ·自产          ●count ◯sig
  ·自产          ●result
```

- 出现条件:**存在未入组 data_out**(实测只有 auto 节点有,Clock/Simulate)。
- 数据点 + 信号口配对规则同方法带输出。
- 头部 ▶ 徽标已声明"自走",此带回答"自走产出什么"。

## 6. 运行态可视化(世界运行时,由 WS 快照驱动)

| 状态 | 视觉 |
|---|---|
| 信号电平 高/低 | 环内绿/红(含信号栏、方法带迷你环、边的颜色)——沿用 v1 |
| 组刚触发(fresh / trigger_fresh) | 方法名 + 连词符短暂高亮脉冲(~300ms) |
| 状态字段 | **运行读值带**:`count=12 · lines=5` 逐字段上脸;值 > 24 字符截断加 `…`;未运行时不显示 |
| 缓冲未消费(fresh 端口) | 对应端口点短暂脉动 |
| 熔断(circuit_open) | 节点红边框 + 头部 `⚠`;fault_count 显示在 tooltip |
| 异步等待(state.pending 存在) | 头部 `⏳` 徽标(LlmCall/Simulate 等待中) |

## 7. 带出现决策表(由声明派生)

```
头部            = 总是
方法带          = 每个 groups 条目各一条(存在组即有)
信号栏          = control_in 或 control_out 非空
源产出带        = 存在未入组 data_out(≈ auto 节点)
运行读值带      = 运行时(state 字段数 > 0)
配置带          = 实例 config 覆盖非空,且节点被选中(或 hover)
```

任何新节点类型套用此表即可,编辑器无需特判(Input/Output 的注入 UI/控制台对接除外,见 §10)。

## 9. 边与连接

- **边颜色沿用 v1 系统**(已证明有效):数据边蓝、信号边按电平绿/红、连触发入口的数据边蓝→黄渐变、连触发入口的信号边纯黄。
- **句柄 id 约定完全不变**:`{in|out}:{slot}:{端口名}`——GraphCanvas 的边映射 / onConnect / 校验逻辑零改动。
- **连接增强(可选)**:用 React Flow store 的 `connectingHandleId` 感知拖线进行中——拖信号线时,把各节点上数据端口的迷你信号环提亮、非目标端口变暗;拖数据线时同理反向。不实现也不影响正确性(拖放校验已存在)。

**风险点**:
- 方法带内端口横排 → 长方法(LlmCall complete 带 2 端口)撑宽节点;实测端口名短,可接受;超宽时端口换行排第二行(实现时加 `flex-wrap` 兜底)。
- 触发入口 ⚡ 句柄位置变化 → 既有图的连线在加载时按句柄 id 重连,位置由新布局决定,无需迁移。
- fresh 动画依赖快照新鲜标记,轮次间可能瞬闪——用 run_no 作为动画 key 避免抖动。

## 11. 开放问题(默认采用推荐项,可随时推翻)

1. **信号面常显 vs 连接时显**:推荐常显(迷你环 4px 静默,不干扰;连接时再提亮)。备选:完全隐藏,仅拖信号线时浮现——更干净但需 connectingHandleId 支持。
2. **配置带显示时机**:推荐"选中/hover 显示,且只显示实例覆盖值"。备选:常显全部 config(信息多,噪音大)。
3. **Input 注入栏位置**:推荐移到节点面(选中时浮现,交互更直接);现状在侧栏。备选:保持侧栏不动。
4. **行高**:推荐 26px(紧凑画布)。若实机观感拥挤可退 30px,纯 CSS 参数。
